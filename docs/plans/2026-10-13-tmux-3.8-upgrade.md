# tmux 3.4 → 3.8 upgrade — plan (2026-10-13)

Owner decision 2026-10-13: upgrade, as its own planned action (recommendation from the 2026-10-12 QoL pass,
[delivery record](./2026-10-12-qol-modernization.md)). This file is the plan and the measured groundwork.
**Dev switched to 3.8 on 2026-10-13 at 07:38 UTC** (step 2 below) and **production at 10:03 UTC** the same
day, when the owner asked for it right after the promotion (step 3). `/usr/bin/tmux` (3.4) no longer works on
either DeckTerm socket.

## Result so far

- tmux 3.8 is built in a private prefix, `/home/deploy/opt/tmux-3.8/bin/tmux`. No system package changed.
  `/usr/bin/tmux` is still 3.4 and every running DeckTerm tmux server is still 3.4.
- DeckTerm now pins the tmux 3.8 default changes that would break it (`581660e`): `mouse off` and
  `theme terminal`, set server-wide together with `history-limit` on every session create. On tmux 3.4
  this changes nothing. Test: `backend/services/tmux-server-options.test.ts` (red on 3.8 before the fix).
- The full unit suite with tmux 3.8 first on `PATH` (every test that starts its own tmux server then runs
  3.8): 1639 pass / 0 fail on 2026-10-13. The Playwright suite still has to run on dev after the dev switch.
- **The switch cannot be gradual.** Measured on 2026-10-13 with private sockets:

| Client → server | Plain commands (`ls`, `new-session -d`, `pipe-pane`, `capture-pane`, `resize-window`) | `attach-session` |
| --- | --- | --- |
| 3.4 → 3.4 | work | works |
| 3.8 → 3.8 | work | works |
| 3.8 → 3.4 | work | **fails**: `open terminal failed: not a terminal` |
| 3.4 → 3.8 | **fail**: `server exited unexpectedly` (the server survives) | fails |

  Both binaries report `PROTOCOL_VERSION 8`, but the messages differ. DeckTerm attaches on every terminal
  open, so a DeckTerm instance must use one tmux version for client and server. Switching an instance
  therefore means stopping its tmux server, which ends that instance's sessions.

## What 3.8 brings DeckTerm

- **Synchronized output** (DECSET 2026, since 3.7): applications can ask for flicker-free redraws. This is
  the main gain of an xterm.js 6 upgrade too, so the two upgrades belong in this order: tmux first.
- **OSC 133 events** (new in 3.8: `pane-command-started`, `pane-command-finished`, `pane-shell-prompt`): tmux understands shell prompt marks.
  DeckTerm could learn about command start and finish from tmux instead of its 2 s polling, which would fix
  "short commands (< about 2 s) may not show running or a completion alert".
- **OSC 9;4 progress** is kept in pane format variables (DeckTerm already parses it from the pipe).
- Changed defaults that DeckTerm must neutralise: `mouse` on (pinned off), builtin colour `theme` (pinned
  `terminal`), a new `C-b T` binding (harmless), copy-mode tweaks (DeckTerm drives copy mode only for
  scrollback). `status` is already turned off per session.

## How the build was made (repeatable, no root)

```bash
B=~/opt/tmux-build; S=$B/sysroot
cd $B/debs && apt-get download libevent-dev libncurses-dev byacc   # Ubuntu-signed packages
for d in *.deb; do dpkg-deb -x "$d" $S; done
cd $B/src && gh release download 3.8 -R tmux/tmux -p 'tmux-3.8.tar.gz'
sha256sum tmux-3.8.tar.gz   # e79c699c7e949dccd0a4a125e17b8d1261e311b16979dbc8eb34542f3966d82e = GitHub asset digest
tar xzf tmux-3.8.tar.gz && cd tmux-3.8
PATH="$S/usr/bin:$PATH" ./configure --prefix=$HOME/opt/tmux-3.8 YACC=byacc \
  LIBEVENT_CORE_CFLAGS="-I$S/usr/include" LIBEVENT_CORE_LIBS="$S/usr/lib/x86_64-linux-gnu/libevent_core.a" \
  LIBEVENT_CFLAGS="-I$S/usr/include" LIBEVENT_LIBS="$S/usr/lib/x86_64-linux-gnu/libevent_core.a" \
  LIBTINFO_CFLAGS="-I$S/usr/include" LIBTINFO_LIBS="-l:libtinfo.so.6" CPPFLAGS="-I$S/usr/include"
PATH="$S/usr/bin:$PATH" make -j4 && make install
```

libevent is linked statically; the only shared dependency beyond libc is the system `libtinfo.so.6`.
Security updates of tmux no longer arrive through `apt` for this binary: rebuild on each tmux release.

## How DeckTerm finds tmux

Every call is `tmux` resolved through `PATH` (backend `Bun.spawn(["tmux", ...])`, the server launcher and
shutdown helper). Both user units set `PATH` explicitly, so a drop-in that puts the 3.8 prefix first
switches one instance:

```ini
# ~/.config/systemd/user/deckterm-dev.service.d/tmux-3.8.conf
[Service]
Environment=PATH=/home/deploy/opt/tmux-3.8/bin:/home/deploy/.local/bin:/home/deploy/.bun/bin:/usr/local/bin:/usr/bin:/bin
```

Manual `tmux -S <DeckTerm socket> …` from a shell must then use the same binary.

## Steps

1. **Dev, code (done):** `581660e` on `dev`; takes effect at the next dev restart, harmless on 3.4.
2. **Dev, switch — done 2026-10-13 07:38 UTC** (one idle dev shell ended; startup reconcile closed its row
   cleanly). The dev tmux server reports `3.8 mouse=0 theme=terminal`; the system 3.4 client gets
   `server exited unexpectedly` on the dev socket, as measured. Full Playwright suite on 4174 with the
   3.8 server: 186 pass / 0 fail, no retries. Procedure used
   (needs a moment when dev sessions may end): close or accept losing the dev sessions;
   `systemctl --user stop deckterm-dev.service`; stop the dev tmux server (its socket is
   `~/.deckterm-dev/tmux/deckterm_deckterm.sock`, never the production one); add the drop-in;
   `systemctl --user daemon-reload && systemctl --user start deckterm-dev.service`.
   Check: `tmux -V` inside a dev terminal's server (`#{version}`), full `test:unit` with 3.8 on `PATH`,
   full Playwright suite on 4174, a visual check of scrolling, selection and resize on desktop and phone.
3. **Production — done 2026-10-13 10:03 UTC.** The owner asked for the switch right away, on condition
   that the operator Claude Code session (which ran in the only production session) would continue
   afterwards. A detached script (transient user unit, outside the tmux server it stopped) did the switch
   in about 4 seconds of downtime:
   1. stopped `deckterm.service`, which detaches and keeps tmux because `KillMode=process`;
   2. stopped the production tmux 3.4 server (only its socket, by process ID);
   3. wrote `~/.config/systemd/user/deckterm.service.d/tmux-3.8.conf` (the same `PATH` line as dev) and ran
      `daemon-reload`;
   4. started a tmux 3.8 server on the production socket with the service environment (unit
      `EnvironmentFile` + `Environment`), the pinned options (`history-limit 10000`, `mouse off`, `theme
      terminal`), and a new session **with the same name as the operator's terminal**
      (`deckterm_deckterm_<terminal id>`, cwd, `bash --rcfile /tmp/deckterm-bash-integration.rc -i`);
   5. started the service: it found that session alive, kept the catalog row active and logged
      `Recovered session`, and the open browser tab reconnected to the same terminal ID;
   6. typed `claude --resume <conversation id> '<continue prompt>'` into the session, so the operator
      continued with its full context.

   The script would have rolled back to 3.4 only if the service had not come up, and would have stayed
   on 3.8 without the operator session if only the recovery had failed. Neither happened. Checked
   afterwards: the production socket reports `3.8`, `mouse off`, `theme terminal`, `history-limit 10000`;
   the 3.4 client gets `server exited unexpectedly`; the old server, its pipe `cat` and the old panes are
   gone; dev was untouched (same service process since 07:38). Log kept in that session's scratchpad.

   **Until the next host reboot**, the production tmux server lives in its own transient
   `deckterm-tmux-prod-<epoch>.scope`, not in `deckterm.service`, because the script started it. It
   behaves the same way (service restarts and deploys keep it, a reboot ends it) and after a reboot the
   service starts tmux inside its own cgroup again, as before.

   The same technique (pre-create the session under the terminal's tmux name, then start the service)
   keeps one chosen terminal reachable under the same ID across any tmux server replacement. Its
   processes still restart, so the session gets a new shell.
4. **Afterwards (own slices):** use tmux OSC 133 hooks for command start and finish; then the xterm.js 6
   upgrade with synchronized output.

Rollback: remove the drop-in, stop the instance's tmux server (sessions end again), start the service.
Only do that with the matching binary: on both sockets that is now `/home/deploy/opt/tmux-3.8/bin/tmux`.

## Open points

- OS-isolation mode (brokered per-user tmux, off in production): the broker's allowlist in
  `scripts/broker/deckterm-broker` accepts only `set-option -t <name> status on|off`, so the brokered
  backend's existing server-wide `history-limit` call is already rejected there, and `mouse off` would be
  too. Extend the allowlist (a privileged script: needs its own security review) before running brokered
  sessions on tmux 3.8.
