# DeckTerm project audit — 2026-09-05

DeckTerm has a substantial, working feature set and passing regression tests. It also has material release-safety and dependency defects, several settings that do not affect behavior, and gaps in keyboard interaction. The recommended next step is a bounded reliability and security repair, followed by UX consolidation. A framework rewrite or a large feature expansion is not justified by this audit.

This is an analysis, not an implementation or production security certification. Application code, production services, access configuration, and dependencies were not changed. Tests used the development service on loopback port 4174 or isolated fixtures. Production configuration was inspected read-only; no HTTP or browser tests targeted port 4173. The pre-existing `.omo/` directory was preserved.

**Fix before the next production promotion**

1. **The candidate release shares live production state.** `scripts/deploy_release.sh:91–92` links the production environment file into the candidate, then line 118 changes only `PORT` and `HOST`. The candidate inherits the production state directory and tmux namespace. Startup opens/migrates the database (`backend/services/foundation-state.ts:809–810`), reconciles session rows, and recovers live tmux sessions (`backend/server.ts:10000–10018`) before the candidate health check approves the release. The source explicitly acknowledges the missing state-directory ownership lock at `backend/server.ts:9981–9985`.

   A rejected candidate can already have changed production data. Reverting a release symlink cannot undo a database migration. This is a confirmed execution-path defect; it is not proof that it caused the historical false-ended session incidents. Give candidate validation a consistent SQLite snapshot, a private tmux socket/namespace, and disabled host-side maintenance effects. Keep the production migration in the promotion step with a verified backup and schema compatibility policy. Acceptance must prove that both accepted and deliberately failed candidates leave live database rows and tmux identities untouched before promotion. A snapshot alone does not isolate external side effects.

2. **Hono is behind applicable security fixes.** Dev and prod install Hono `4.11.3`. `bun audit --json` returned 36 advisory records in this dependency: 4 high, 29 moderate, and 3 low. These are package advisory counts, not 36 demonstrated DeckTerm vulnerabilities. A relevant path is confirmed: global `cors()` at `backend/server.ts:5324–5334` uses the default header parser before authentication. The installed parser has quadratic behavior for a crafted `Access-Control-Request-Headers` preflight header. The official [CORS advisory](https://github.com/honojs/hono/security/advisories/GHSA-8j4g-w8fx-2239) identifies versions below `4.12.34` as affected.

   Upgrade to a current compatible Hono release, pin the resulting lockfile, and supply an explicit CORS header allowlist. Retain JWT, capability, file-boundary, WebSocket, and browser regression checks. This audit established reachability inside the application origin; it did not send a denial-of-service payload to the running service or establish bypass of the Cloudflare edge. Hono JWT/JWK advisories are not automatically applicable to the separate Cloudflare verification implementation.

3. **Cloudflare signing-key caching is inverted in the installed middleware.** `@hono/cloudflare-access` `0.3.1`, used at `backend/server.ts:5342`, refreshes signing keys while its cache is still valid, then fails to refresh after expiration (`node_modules/@hono/cloudflare-access/dist/index.js:13`). An isolated probe generated a temporary public RSA key and mocked time and network access. Fetch counts were `1 → 2 → 2` for cold, fresh, and expired cache states. No real credentials were used.

   This adds a Cloudflare network dependency to normal authenticated requests and can prevent login after signing-key rotation following an idle period. The [current official implementation](https://raw.githubusercontent.com/honojs/middleware/main/packages/cloudflare-access/src/index.ts) corrects expiration and retries unknown signing keys; [version 0.4.0](https://raw.githubusercontent.com/honojs/middleware/main/packages/cloudflare-access/CHANGELOG.md) includes authentication hardening. Upgrade deliberately and pass the application audience into the middleware, preserving the current audience and fail-closed configuration checks. Test fresh/expired caches, rotation, bad audience, missing claims, and provider failure.

4. **Regular recoverable backups are not demonstrated on this host.** The newest inspected local production database backup manifest is dated 2026-08-19; the dev manifest is dated 2026-07-04. No corresponding DeckTerm timer or matching readable cron schedule was found, although `docs/upgrade-and-backup-runbook.md:83` calls for daily scheduling. No automatic predeployment backup was found in the release script. Host-wide and off-host backups were not inventoried, so this is an evidence and local automation gap, not a claim that no backup exists anywhere.

   Establish one documented daily backup owner, a retained off-host copy, age/failure alerts, and an isolated restoration drill. Use a SQLite-consistent backup, not an arbitrary copy of a live database file. A successful backup command must be distinguished from a demonstrated restore.

**Design and quality-of-life improvements worth doing**

The existing dark terminal surface is coherent and gives the terminal most of the screen. Desktop and narrow layouts were usable without horizontal document overflow. Keep that foundation and make a focused pass over navigation and forms.

| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Put server diagnostics under Advanced or Setup      | Appearance currently places one accent control above a long server-configuration block; on mobile diagnostics dominate the screen    | Small UX change; retain authorized access to diagnostics                                                                                                      |
| Simplify the Tools panel hierarchy                  | Setup, settings, copy, layout operations, and help currently have similar visual weight; “Compact Navigation” adds little user value | Group by task; prioritize common actions and use one spacing/button system                                                                                    |

Preserve existing restoration and avoid automatically refreshing an active terminal                                  |
| Finish behavior before adding more settings         | Six ineffective options make the UI promise more than it provides                                                                    | Observable setting contracts and a clear distinction between live-applied, next-session, and unavailable options                                              |
| Reduce duplicate implementation paths incrementally | `web/app.js` has 14,831 lines and `web/styles.css` 8,305; legacy and IDE surfaces drift, as the two Git diff keys show               | Extract shared behavior by surface during fixes. Small fine-pointer controls deserve a sizing pass, but this audit does not declare a blanket WCAG target-size violation: [WCAG 2.2 permits spacing exceptions](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Touch-specific close controls already have smoke coverage. Gemini CLI was unavailable, so screenshot review was manual; no automated image-diff baseline was available or claimed.

**Features already present, and deliberate limits**

- Persistent tmux sessions, reconnect/replay, workspace tabs, split/tiled panes, linked views, session attach/restore, layout undo, terminal search, multiline/image paste, mobile extra keys, completion sounds, and push notification support already exist.
- Files, a CodeMirror editor, autosave, external-change conflict warnings, editor tabs, Git staging/commits/stash/branches/history/diffs, workspace search/replacement, a command palette, and task list/board workflows already exist. Suggestions should improve their consistency rather than introduce duplicate surfaces.
- Production authentication is not anonymous. Cloudflare team/audience startup guards, capability checks, disabled-user precedence, allowed file roots, rate limiting, and fail-closed OS isolation paths are present and tested.
- Application roles are not Unix isolation. With `DECKTERM_OS_ISOLATION` off, terminal users share the service account. Before admitting mutually untrusted users, validate mapped Unix accounts and all enabled surfaces. Turning isolation on is not a cosmetic toggle: task execution, network Git, and workspace search have intentionally denied paths documented in `docs/security-model.md`. Generic company OIDC remains a deferred integration rather than a defect in the current Cloudflare setup.
- The historical false-ended session-catalog race remains a follow-up in project records; this audit did not reproduce it or establish its cause. The unsafe candidate state-sharing path above is independently verified.

**Testing and documentation follow-ups**

`web/bootstrap-routing.test.js` is tracked but omitted from the explicit `test:unit`/`test:push` lists; its seven tests passed separately. Include it in the gate or use a test census that detects omissions. TypeScript is not pinned in the root package; pin the compiler used by CI so local and CI typechecking use the same version. Update the project map: `AGENTS.md` still describes a two-dependency terminal and no longer captures the broker, state, editor, tasks, and wider frontend architecture. These are maintenance gaps, not evidence of a broken build.

Recommended delivery order: isolate candidate state and prove backup/restore; update the two authentication/server dependencies; implement Origin/CSRF and transfer budgets; repair ineffective settings and dialog focus; then consolidate Tools/Settings/Files design and add reversible file deletion. Keep each change independently reviewable. Production promotion remains a separate authorized deployment action.
